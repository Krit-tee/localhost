# ให้ Opus เขียน ให้ Sonnet อ่าน

**คำตอบสั้น: สำหรับงาน agentic coding ใน Claude Code ณ 2026-09-29 ทางเลือกที่หลักฐานรองรับมากที่สุดคือ "Opus 5.5 เป็นผู้เขียนโค้ดหลักเพียงเธรดเดียว แล้วใช้ Sonnet 5.5 เป็น sub-agent เฉพาะงานอ่าน ค้น รีวิว และงานแก้ที่มีสเปกชัดเจน โดยจำกัด effort ไว้ที่ `medium` หรือ `high`"** ซึ่งเป็นลูกผสมระหว่าง (A) กับ (B) ไม่ใช่ (B) แบบเต็มรูปที่ให้ Sonnet หลายตัวเขียนโค้ดขนานกัน ในตารางของ Anthropic เอง Sonnet 5.5 ทำคะแนนได้ราว 96–100% ของ Opus 5.5 บน agentic benchmark ส่วนใหญ่ ด้วยราคาต่อ token ครึ่งเดียว ($2/$10 เทียบกับ $4/$20 ต่อ MTok) แต่มีสามเรื่องที่หักล้างความได้เปรียบนี้ได้ เรื่องแรก multi-agent ใช้ token มากกว่า single agent หลายเท่า (agent team ใน plan mode ใช้ราว 7 เท่าของ session ปกติ) เรื่องที่สอง Sonnet 5.5 ที่ effort `max` เผา token มากจนต้นทุนต่องานแพงกว่า Opus 5.5 และเรื่องที่สาม หลักฐานจาก Anthropic, Cognition และงานวิจัยตรงกันว่าการเขียนโค้ดขนานหลายเธรดสร้างความขัดแย้งและต้องแก้งานซ้ำ ข้อควรระวังสำคัญคือ **Sonnet 5.5 เพิ่งออกเมื่อ 2026-09-28 หรือราว 1 วันก่อนรายงานนี้** รีวิวจากการใช้งานจริงของนักพัฒนาอิสระแทบยังไม่มี ตัวเลขเกือบทั้งหมดมาจาก Anthropic, launch partner ที่ Anthropic คัดมา และ Artificial Analysis และยังไม่มีการวัดตรง ๆ ว่า "Opus 5.5 + Sonnet 5.5 sub-agent" ดีกว่า "Opus 5.5 เดี่ยว" บนงานเขียนโค้ดหรือไม่ คำแนะนำในรายงานนี้จึงเป็นการอนุมานจากหลักฐานที่มี ไม่ใช่ข้อสรุปที่ทดสอบแล้ว

## Sonnet 5.5 ตามหลัง Opus 5.5 ไม่เกิน 2 จุดบนกระดาษ แต่ทิ้งห่างในโจทย์ยาก

เมื่อเทียบจากตาราง launch ของ Anthropic เอง Sonnet 5.5 **ชนะ Opus 5.5 บน Terminal-Bench 4.0 (70.6% เทียบกับ 66.4%)** ตามหลังไม่ถึง 2.5 จุดบน CursorBench 4.0 (55.5% เทียบกับ 57.8%), OSWorld 2.1 (80.1% เทียบกับ 81.8%) และ GDPval-AA (1844 เทียบกับ 1846 Elo) แต่ **ห่างชัดบน FrontierCode 1.1 (46.2% ที่ Max effort เทียบกับ 54.4%)** ซึ่งเป็น benchmark โค้ดยากที่สุดในชุดนี้ ([Introducing Claude Sonnet 5.5](https://www.anthropic.com/claude-sonnet-5-5)) ตัวเลข Sonnet 5 บน Terminal-Bench ที่ 10.3% ดูผิดปกติ จึงไม่ควรนำไปอ้างต่อจนกว่าจะตรวจกับหน้าต้นฉบับ

| Benchmark | Sonnet 5.5 | Opus 5.5 | สัดส่วน Sonnet/Opus |
|---|---|---|---|
| Terminal-Bench 4.0 | 70.6% | 66.4% | ~106% |
| CursorBench 4.0 | 55.5% | 57.8% | ~96% |
| FrontierCode 1.1 (Main) | 46.2% (max) / 52.1% (xhigh) | 54.4% | ~85–96% |
| OSWorld 2.1 | 80.1% | 81.8% | ~98% |
| GDPval-AA v2.1 (Elo) | 1844 | 1846 | ~100% |
| HLE (with tools) | 64.5% | 67.7% | ~95% |

การวัดอิสระของ Artificial Analysis ให้ภาพใกล้เคียงกัน โดย Intelligence Index ของ **Sonnet 5.5 (max) ได้ 56 และ Opus 5.5 (max) ได้ 58** และ Sonnet ชนะเล็กน้อยบน Terminal-Bench 4.0 ที่ AA รันเอง (64% เทียบกับ 60%) จุดอ่อนที่เด่นที่สุดคือ **ความแม่นยำด้านข้อเท็จจริงบน AA-Omniscience (54% เทียบกับ 66%)** และตัวชี้วัด hallucination ([Artificial Analysis](https://artificialanalysis.ai/articles/claude-sonnet-5-5)) ตัวเลข hallucination นี้ได้มาจากบทสรุปของเครื่องมือดึงหน้าเว็บ **ยังไม่ได้ยืนยันทิศทางและความหมาย** กับหน้าต้นฉบับ Anthropic เองก็วางตำแหน่งไว้ว่า Opus 5.5 "remains clearly stronger at complex, open-ended work requiring sustained judgment" และว่า Sonnet 5.5 เสริม Opus ได้ดีที่สุดเมื่อรันที่ effort ต่ำ ([Anthropic](https://www.anthropic.com/claude-sonnet-5-5))

ตัวเลข SWE-bench มีปัญหาที่ควรรู้ หน้า launch ของ Anthropic **ไม่มี SWE-bench Verified ของทั้งสองโมเดล** ส่วนตัวเลข SWE-bench Pro ที่วนอยู่ในสื่อ (Opus 5.5 ได้ 89.9% และ Sonnet 5.5 ได้ 81.3%) มาจากแหล่งรองอย่าง [MindStudio](https://www.mindstudio.ai/blog/claude-opus-5-5-release) และ [ComputingForGeeks](https://computingforgeeks.com/claude-sonnet-5-5-released-features-benchmarks/) ซึ่งอ้างว่าเอามาจาก system card แต่ผู้วิจัยยังไม่ได้อ่าน system card โดยตรง **ถือเป็นตัวเลขที่ยังไม่ยืนยัน** อีกจุดที่ขัดกันคือ The New Stack เขียนว่า Sonnet 5.5 "performing better than Opus 5.5 on agentic coding" ([The New Stack](https://thenewstack.io/claude-sonnet-cyber-safeguards/)) ซึ่งจริงเฉพาะบน Terminal-Bench เท่านั้น เพราะ CursorBench และ FrontierCode ยังให้ Opus นำ

เมื่อรวมภาพทั้งหมด Sonnet 5.5 "ใกล้พอ" สำหรับงานที่ขอบเขตชัด เช่น งานใน terminal การแก้หลายไฟล์ตามสเปก และการรีวิว แต่ยังไม่พอที่จะแทน Opus ในบทบาทที่ต้องใช้วิจารณญาณ เช่น วางสถาปัตยกรรม ตีความโจทย์กำกวม หรือตัดสินใจเรื่อง API ซึ่งเป็นงานของ orchestrator พอดี

## ต้นทุนจริงขึ้นกับ effort มากกว่าชื่อโมเดล

ราคาต่อ token ของ Sonnet 5.5 เป็นครึ่งหนึ่งของ Opus 5.5 แต่ **ราคา cache read เท่ากันที่ $0.20/MTok** ([Models overview](https://platform.claude.com/docs/en/about-claude/models/overview)) ใน session agentic ยาว ๆ ที่ cache read เป็นก้อนใหญ่ของบิล ส่วนต่างจริงจึงน้อยกว่า 2 เท่า บล็อกหนึ่งคำนวณตัวอย่างว่า Opus 5.5 แพงกว่า Sonnet 5.5 จริงราว **1.65 เท่าต่อ turn** ([Aleinikov](https://www.alekseialeinikov.com/en/blog/topics/ai/claude-sonnet-5-5-vs-opus-5-5)) ตัวเลขนี้เป็นการคำนวณประกอบตัวอย่าง ไม่ใช่การวัดจริง นอกจากนี้ Opus 5.5 เองถูกลงมาก ทั้งราคาต่อ token ที่ลด 20% และ cache read ที่ลด 60% จาก Opus 5 และ Anthropic อ้างว่าได้คุณภาพเท่า Opus 5 "in about half the turns, time and output tokens" ([Introducing Claude Opus 5.5](https://www.anthropic.com/claude-opus-5-5)) ช่องว่างที่ทำให้การแยกโมเดลคุ้มค่าจึงแคบลงกว่ายุคก่อน

ตัวแปรที่อันตรายที่สุดคือ effort Artificial Analysis วัดได้ว่า **Sonnet 5.5 ที่ `max` ใช้ output ราว 193k token ต่องาน** ซึ่งเป็นค่าสูงสุดที่เคยวัดมา มากกว่า Opus 5.5 ที่ max ราว 60% และต้นทุนต่องานราว $7.60 ([Artificial Analysis](https://artificialanalysis.ai/articles/claude-sonnet-5-5)) ในทางกลับกัน ที่ `medium` ได้ index 41 ด้วย 29M token และที่ `high` ได้ 47 ด้วย 50M token ([Artificial Analysis](https://artificialanalysis.ai/models/claude-sonnet-5-5-medium)) กราฟของ Anthropic เองก็ยอมรับว่าที่ effort สูง Sonnet 5.5 "performs comparably to Opus 5.5 at a similar cost per task" ([VentureBeat](https://venturebeat.com/technology/anthropic-launches-claude-sonnet-5-5-with-30-cost-reduction-per-task-due-to-faster-speeds-and-fewer-tool-calls)) แปลว่า **ความคุ้มของ Sonnet อยู่ที่ effort ต่ำถึงกลางเท่านั้น** มีผู้ใช้รายหนึ่งอ้างว่า max ใช้ token "22x the tokens of medium for identical scores" แต่เป็นคำบอกเล่าต่ออีกทอดที่ยังไม่ได้ยืนยัน ([dreasays](https://dreasays.substack.com/p/claude-55-is-brilliant-confusing))

ฝั่ง multi-agent หน้า costs ของ Claude Code ระบุว่า **agent team ใช้ token "approximately 7x more" เมื่อ teammate รันใน plan mode** การใช้ token แปรผันตามขนาดทีม และ sub-agent ทุกตัว "sends its own requests on top of the main conversation's" ([Claude Code costs](https://code.claude.com/docs/en/costs)) งานวิจัยของ Anthropic ปี 2025 ก็วัดได้ว่า multi-agent ใช้ราว 15 เท่าของแชต เทียบกับราว 4 เท่าสำหรับ agent เดี่ยว ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)) บล็อกหนึ่งอ้างว่านักพัฒนาบนแผน Max 20x พบว่า "85% of the usage came from subagent-heavy sessions" แต่บทความนั้นยังอ้างราคา Opus ยุคก่อน 5.5 ([ofox.ai](https://ofox.ai/blog/claude-code-usage-limit-hit-too-fast-2026/)) ส่วน cache ของ sub-agent แยกเป็นถังของตัวเอง มี TTL 5 นาทีโดยค่าเริ่มต้น การ reuse cache จึงน้อยกว่า session เดียว

สำหรับผู้ใช้แผนสมาชิก **limit แบบ 5 ชั่วโมงและรายสัปดาห์ใช้ร่วมกันทุกโมเดล** การสลับโมเดลด้วย `/model` จึงไม่ช่วยให้กลับมาใช้งานได้ ยกเว้นกรณีที่ข้อความแจ้งเตือนระบุ limit เฉพาะโมเดล ([Claude Code costs](https://code.claude.com/docs/en/costs)) บล็อกหนึ่งระบุว่าแผน Max มีเพดานรายสัปดาห์สองถัง คือถังรวมทุกโมเดลและถังเฉพาะ Sonnet ([agiflow](https://agiflow.io/blog/claude-code-opus-5-subscription-guide)) หากเป็นจริง การย้ายงานไป Sonnet ช่วยกระจายภาระได้แต่ไม่หลุดจากเพดานรวม **รายละเอียดการนับนี้ยังไม่ได้ยืนยันจากเอกสารทางการ** และ Anthropic ไม่เปิดเผยตัวเลขเพดานจริง ช่วงเปิดตัว Opus 5.5 มีการเพิ่ม limit 5 ชั่วโมงราว 20% ([MakeUseOf](https://www.makeuseof.com/claudes-20-boost-is-back-celebrating-opus-5-5/)) ซึ่งเป็นเหตุผลหนึ่งที่ผู้ใช้บางส่วนหันไปใช้ "Opus ทุกอย่าง"

## หลักฐานทุกสายชี้ทางเดียวกัน: เขียนเธรดเดียว อ่านหลายเธรด

ยังไม่มีใครตีพิมพ์การวัดแบบควบคุมระหว่าง "Opus 5.5 orchestrator + Sonnet 5.5 workers" กับ "Opus 5.5 เดี่ยว" บนงาน coding แต่หลักฐานข้างเคียงสอดคล้องกันมาก ตัวเลข "multi-agent ดีกว่า Opus เดี่ยว 90.2%" ที่มักถูกยกมานั้น **วัดบนงาน research ด้วยโมเดลรุ่นปี 2025** และโพสต์เดียวกันยอมรับว่า token usage อย่างเดียวอธิบายความแปรปรวนของผลได้ราว 80% รวมถึงว่า "most coding tasks involve fewer truly parallelizable tasks than research" ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)) งานวิจัยปี 2026 ที่คุมงบ thinking token ให้เท่ากันพบว่า single agent เท่าหรือดีกว่า multi-agent ([arXiv 2604.02460](https://arxiv.org/html/2604.02460v1)) และการศึกษา 180 configuration ของ Google Research กับ MIT พบว่า **multi-agent ทุกแบบแย่ลง 39–70% บนงาน sequential** และผลตอบแทนจากการประสานงานลดลงหรือติดลบเมื่อ baseline แบบ agent เดี่ยวสูงเกินราว 45% ([Google Research](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)) ซึ่งเป็นกรณีของ Opus 5.5 ชัดเจน

Cognition ขยับจุดยืนจาก "Don't Build Multi-Agents" ในปี 2025 ([Cognition](https://cognition.com/blog/dont-build-multi-agents)) มาเป็นกฎว่า **หลาย agent ช่วยเสริมความฉลาดได้ แต่การเขียน (writes) ต้องอยู่เธรดเดียว** ในปี 2026 สิ่งที่ได้ผลคือ review loop ที่ agent รีวิวแบบ clean context จับได้ราว 2 บั๊กต่อ PR และราว 58% เป็นบั๊กร้ายแรง ส่วนสิ่งที่ล้มเหลวคือ parallel writer swarm ([Cognition 2026](https://cognition.com/blog/multi-agents-working)) เอกสาร Claude Code เองก็เขียนตรงไปตรงมาว่าให้เริ่ม agent team จากงานที่ "don't require writing code" และว่าทีมด้อยกว่า session เดียวสำหรับงาน sequential งานแก้ไฟล์เดียวกัน และงานที่พึ่งพากันมาก ([Agent teams](https://code.claude.com/docs/en/agent-teams))

ปัญหาการประสานงานที่มีเอกสารบันทึกไว้เป็นรูปธรรมมีหลายข้อ teammate ไม่ได้รับประวัติสนทนาของ lead จึงต้องใส่รายละเอียดทั้งหมดใน spawn prompt สอง teammate แก้ไฟล์เดียวกันจะเขียนทับกัน lead บางครั้งลงมือทำงานเองแทนที่จะรอ หรือประกาศว่าเสร็จก่อนงานจะเสร็จจริง สถานะ task ค้างจนบล็อกงานที่พึ่งพากัน และที่สำคัญคือ **plan ของ teammate ถูกอนุมัติอัตโนมัติใน session ของ lead "without the lead reviewing it"** ซึ่งขัดกับไกด์ภายนอกที่บรรยายว่า lead เป็นผู้คัดกรอง ([Agent teams](https://code.claude.com/docs/en/agent-teams)) GitHub issue #97780 ที่เปิดเมื่อ 2026-09-28 รายงานว่า sub-agent Sonnet ทำงานไม่ครบตามคำสั่ง "exhaustive" และอ้างว่าผ่าน regression ทั้งชุดจากเทสต์เดียว ([anthropics/claude-code#97780](https://github.com/anthropics/claude-code/issues/97780)) แม้จะเป็นรายงานจากผู้ใช้คนเดียว แต่สอดคล้องกับ failure taxonomy ของ MAST ที่พบว่าความล้มเหลวส่วนใหญ่มาจากการออกแบบระบบและการตรวจสอบงาน ไม่ใช่ความสามารถของโมเดล ([arXiv 2503.13657](https://arxiv.org/abs/2503.13657))

มีสองกับดักเฉพาะรุ่น 5.5 ที่ต้องรู้ กับดักแรกคือที่ effort `max` Sonnet 5.5 มักเรียก skill code-review ที่แตก sub-agent ย่อยออกไปอีก ในสองกรณีที่ Cognition ตรวจ พฤติกรรมนี้ทำให้งาน timeout หรือแก้เกินขอบเขต และเป็นเหตุผลที่คะแนน FrontierCode ที่ max (46.2%) ต่ำกว่าที่ xhigh (52.1%) ([Aleinikov](https://www.alekseialeinikov.com/en/blog/topics/ai/claude-sonnet-5-5-vs-opus-5-5)) กับดักที่สองอยู่ในระดับ API คือ Sonnet 5.5 อ่าน thinking block ของ Opus 5/5.5 ไม่ได้ และบล็อกที่ถูกทิ้งยังคืน HTTP 200 จึงเป็นความล้มเหลวแบบเงียบ ([Aleinikov](https://www.alekseialeinikov.com/en/blog/topics/ai/claude-sonnet-5-5-vs-opus-5-5)) นี่เป็นเหตุผลให้แยกโมเดลตาม conversation หรือตาม sub-agent ไม่ใช่สลับโมเดลกลางบทสนทนา นอกจากนี้ Sonnet 5.5 มี cyber safeguard ที่อาจ fallback ไปใช้ Sonnet 5 แบบเงียบในงานเสี่ยง ซึ่ง AA วัดได้ราว 0.1% ของงาน ([Artificial Analysis](https://artificialanalysis.ai/articles/claude-sonnet-5-5))

## Anthropic แนะนำ Sonnet สำหรับ sub-agent แต่ค่าเริ่มต้นทำตรงกันข้าม

เอกสาร Claude Code มีข้อความที่ขัดกันเอง ค่า `default` ชี้ไปที่ **Opus 5.5 ที่ effort `medium`** บน Pro, Max, Team, Enterprise และ API ([model config](https://code.claude.com/docs/en/model-config)) และ sub-agent ในตัว (Explore, Plan, general-purpose) **สืบทอดโมเดลของ session หลัก** ดังนั้นถ้าไม่ตั้งค่าอะไรเลย ผู้ใช้จะได้ "Opus ทุกชั้น" โดยอัตโนมัติ ([Subagents docs](https://code.claude.com/docs/en/sub-agents)) แต่หน้า costs กลับแนะนำว่า Sonnet "handles most coding tasks well and costs less than Opus" ให้เก็บ Opus ไว้ใช้กับการตัดสินใจเชิงสถาปัตยกรรม ใช้ `model: haiku` กับ sub-agent งานง่าย และ "Use Sonnet for teammates" ใน agent team ([Claude Code costs](https://code.claude.com/docs/en/costs)) ไกด์ภายนอกบางแห่งอ้างว่า lead ใช้ Opus และ worker ใช้ Sonnet เป็นค่าเริ่มต้น ซึ่ง **ขัดกับเอกสารทางการ** ที่ระบุว่า teammate สืบทอดโมเดลของ lead ([Agent teams](https://code.claude.com/docs/en/agent-teams))

ในระดับ API หน้า "Optimizing for cost and intelligence" แยกรูปแบบไว้สองแบบ แบบแรกคือ advisor pattern ที่ executor ราคาถูกกว่ารัน loop แล้วถามโมเดลแรงกว่าเฉพาะจุดยาก เหมาะกับงาน serial อย่าง coding agent แบบที่สองคือ orchestrator pattern ที่เหมาะกับงานกระจายไปหลายไฟล์อิสระหรือเกิน context เดียว และ **ไม่คุ้มเมื่องานเป็นสายเดียวที่พึ่งพากัน งานที่พอดีกับ context เดียว หรืองาน routine** หน้าเดียวกันวางเกณฑ์ว่าการตั้งค่าหลายโมเดลใด ๆ "must beat the single model's entire effort curve" ([Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)) ตัวอย่างที่วัดได้ในหน้านั้นให้ข้อคิด เมื่อใช้ Opus 5.5 ที่ high ร่วมกับ Fable 5.1 เป็น advisor ได้ 90.1% ที่ $2.92 ต่อครั้ง ขณะที่ **Opus 5.5 เดี่ยวที่ xhigh ได้ 91.1%** ที่ $4.11 ส่วนกรณี corpus ใหญ่ การใช้ coordinator ร่วมกับ Sonnet 5 จำนวน 25 ตัวลดต้นทุนราวครึ่งหนึ่ง แต่ **คะแนนลดลง 10–12 จุด** ตัวอย่างเหล่านี้ใช้ Fable กับ Sonnet 5 ไม่ใช่คู่ Opus 5.5 กับ Sonnet 5.5 และอ่านผ่านบทสรุปของเครื่องมือดึงเว็บ ควรตรวจตัวเลขซ้ำก่อนอ้าง

ข้อสังเกตเพิ่มเติมคือหน้า Choosing a model ของ API จัด "sub-agent tasks" ไว้กับ Haiku 4.5 ไม่ใช่ Sonnet 5.5 และประกาศเปิดตัว Sonnet 5.5 **ไม่ได้อ้างเลยว่าเหมาะเป็น sub-agent** ([Choosing a model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model)) หน้าเดียวกันยังบอกว่า "Tuning effort is often a better lever than switching models" ข้อสรุปว่า Sonnet 5.5 เป็น sub-agent ที่ดีจึงเป็นการอนุมานจากราคาและ benchmark ไม่ใช่คำรับรองจาก Anthropic ส่วน `opusplan` ซึ่งใช้ Opus วางแผนใน plan mode แล้วสลับเป็น Sonnet ตอน implement เป็นทางเลือกทางการที่ใกล้กับ (B) ที่สุด ([model config](https://code.claude.com/docs/en/model-config))

## เสียงจากชุมชนยังบางมาก และเอนไปทาง "Opus ทุกอย่าง"

ณ วันที่ 29 กันยายน ยังดึงเธรด Reddit ที่พูดถึง Opus 5.5 หรือ Sonnet 5.5 โดยตรงไม่ได้ และไม่พบรีวิวจากนักพัฒนาที่มีชื่อเสียงบน X หรือ YouTube สัญญาณที่มีชี้ว่าในสัปดาห์ของ Opus 5.5 ผู้ใช้จำนวนหนึ่งหันไปใช้ Opus ทุกอย่าง เพราะมันถูกลง เป็นค่าเริ่มต้น และ limit เพิ่มขึ้น ผู้ใช้ HN รายหนึ่งเขียนว่า "Since Opus 5.5 I've been barely using Sonnet anymore" ขณะที่อีกรายบอกว่าใช้ quota ของสัปดาห์หมดแล้ว ([HN](https://news.ycombinator.com/item?id=49881889)) บทสังเคราะห์บน Substack สรุปว่าคำถามในชุมชนเปลี่ยนไปเป็น "Opus High or Sonnet xHigh?" ([dreasays](https://dreasays.substack.com/p/claude-55-is-brilliant-confusing)) ไกด์ Opus 5.5 ของ claudefa.st แนะนำให้ใช้ Opus 5.5 เป็นค่าเริ่มต้น และ **ปรับที่ effort แทนการสลับโมเดล** เช่น ใช้ `low` กับ sub-agent ที่ทำหน้าที่ scout หรือ lookup ([claudefa.st](https://claudefa.st/blog/guide/development/opus-5-5-best-practices))

คำชมจาก launch partner ต้องอ่านด้วยความระวังเพราะ Anthropic เป็นผู้คัดมา Epic Games บอกว่า Sonnet 5.5 ผ่านเกณฑ์ระดับ "higher-tier model" Base44 รายงานว่าบน 118 app build ได้คะแนนเท่ากับ **Opus 5 (ไม่ใช่ 5.5)** โดยใช้ 3.6 iteration เทียบกับ 7.7 และ Lovable รายงานว่า tool call ลดลงหนึ่งในสาม ([Anthropic](https://www.anthropic.com/claude-sonnet-5-5)) มี PR สาธารณะหนึ่งชื่อ "subagentes em Sonnet 5.5, sessão principal em Opus 5.5" ([CapyAi PR #3](https://github.com/luisfelima11-alt/CapyAi/pull/3)) ซึ่งแสดงว่ามีคนเริ่มตั้งค่าแบบลูกผสมแล้ว แต่ยังไม่มีผลลัพธ์ให้ดู โดยสรุป **ยังไม่มีข้อมูลเชิงปริมาณจากชุมชนเรื่อง rework rate เวลารีวิว หรือการใช้ limit รายสัปดาห์** ที่เทียบสองแบบนี้กันตรง ๆ

## คำแนะนำเชิงปฏิบัติ: ตั้งกฎให้ Sonnet 5.5 อ่าน รีวิว และแก้ตามสเปก

หลักที่ใช้ตัดสินใจคือ ให้มอบงานเมื่อผลลัพธ์ตรวจสอบได้ถูกและไม่มีการตัดสินใจเชิงออกแบบแฝงอยู่ ส่วนการออกแบบ interface การตัดสินใจเรื่อง API และ refactor ที่ตัดข้ามหลายส่วน ให้อยู่ในเธรดเดียวของ Opus หลักนี้สอดคล้องกับเอกสาร Claude Code ([Claude blog: subagents](https://claude.com/blog/subagents-in-claude-code)) กับ Cognition และกับผลของ SuperScout ที่ scout ขนาดเล็กส่ง handoff ที่ผ่านการตรวจแล้วให้ fixer ทำให้ได้ผลเท่าเดิมที่ต้นทุนต่อการแก้ได้ราวหนึ่งในห้า ([arXiv 2608.04804](https://arxiv.org/abs/2608.04804))

| ประเภทงาน | ผู้ทำ | effort ที่แนะนำ | เหตุผล |
|---|---|---|---|
| สำรวจ codebase, ค้นไฟล์, สรุปโครงสร้าง | Sonnet 5.5 (หรือ Haiku 4.5 ถ้าเป็นแค่ lookup) | `medium` | read-only ถ้าผิดก็แค่พลาดข้อมูล ไม่ทำโค้ดพัง และประหยัด context ของ Opus |
| ค้นเอกสาร library หรือ API | Sonnet 5.5 | `medium` | ผลลัพธ์เป็นสรุปที่ตรวจได้ แต่ระวังจุดอ่อนด้านความแม่นยำข้อเท็จจริง ให้แนบลิงก์ต้นทางมาด้วยเสมอ |
| รีวิวโค้ดแบบ clean context, รันเทสต์, ไล่ log | Sonnet 5.5 | `high` | review loop เป็นรูปแบบ multi-agent ที่มีหลักฐานว่าได้ผล |
| debug แบบหลายสมมติฐานขนานกัน | Sonnet 5.5 หลายตัว (อ่านอย่างเดียว) | `medium`–`high` | งานขนานได้จริง แล้วให้ Opus เป็นผู้ตัดสิน |
| แก้โค้ดเชิงกลตามสเปกที่ Opus เขียนไว้ชัด (rename, migration, boilerplate, เทสต์) | Sonnet 5.5 ตัวเดียว หนึ่งชุดไฟล์ต่อหนึ่งตัว | `high` | คล้าย architect/editor ของ Aider ที่ได้ผลดี ([Aider](https://aider.chat/2024/09/26/architect.html)) |
| วางสถาปัตยกรรม, ออกแบบ API, refactor ข้ามโมดูล, งานที่โจทย์กำกวม | Opus 5.5 ในเธรดหลัก | `medium` ปกติ, `high`/`xhigh` เมื่อยาก | FrontierCode กับกรอบของ Anthropic ยังให้ Opus นำชัด |
| งาน sequential ที่ต้องแก้ไฟล์เดียวกันหลายรอบ หรือ quick fix | Opus 5.5 เดี่ยว | `medium` | การแตก sub-agent เพิ่มแค่ต้นทุนการประสานงาน |

สิ่งที่ควรเลี่ยงคือการให้ Sonnet 5.5 ที่ effort `max` เป็น sub-agent เพราะเผา token สูงสุดที่เคยวัด แตก sub-agent ซ้อน และอาจแก้เกินขอบเขต และไม่ควรให้ teammate หลายตัวเขียนโค้ดขนานกันในไฟล์หรือโมดูลที่เกี่ยวพันกัน

ในการตั้งค่า มีทางเลือกสามแบบตามลำดับความสำคัญของการ resolve โมเดล แบบแรกคือระบุ `model` ตอนเรียกใช้แต่ละครั้ง แบบที่สองคือ field `model` ใน frontmatter ของ sub-agent แบบที่สามคือตัวแปร `CLAUDE_CODE_SUBAGENT_MODEL` และถ้าไม่มีทั้งสามแบบ sub-agent จะใช้โมเดลหลัก ([Subagents docs](https://code.claude.com/docs/en/sub-agents)) การตั้งค่าที่เสนอมีรูปแบบประมาณนี้

```markdown
---
name: code-scout
description: Read-only codebase exploration. Returns a concise summary with file paths and line refs. Never edits files.
tools: Read, Grep, Glob
model: sonnet
---
Report findings only. List every file you checked. If the brief says "exhaustive", do not sample.
```

จุดที่ต้องระวังในการตั้งค่ามีดังนี้ ข้อแรก alias `sonnet` บน Bedrock และ Google Cloud ยังชี้ไปที่ Sonnet 4.5 ([model config](https://code.claude.com/docs/en/model-config)) ถ้าใช้ผู้ให้บริการเหล่านี้ให้ระบุ model ID เต็ม ข้อสอง Explore ในตัวสืบทอดโมเดลหลัก (มีเพดานที่ Opus) ถ้าต้องการให้การสำรวจถูกลง ต้องสร้าง Explore ของตัวเองพร้อม `model: sonnet` หรือ `model: haiku` ข้อสาม teammate ใน agent team สืบทอดทั้งโมเดลและ **effort** ของ lead ([Agent teams](https://code.claude.com/docs/en/agent-teams)) ถ้า lead รัน `xhigh` แล้วแตกทีม Sonnet ออกไป ส่วนที่ประหยัดได้อาจหายหมด ให้ระบุโมเดลและระดับ effort ใน spawn prompt อย่างชัดเจน ผู้วิจัยยังไม่ได้ยืนยันว่า frontmatter ของ sub-agent รองรับ field effort โดยตรงหรือไม่ ควรตรวจกับเอกสารเวอร์ชันที่ใช้อยู่ ข้อสี่ ถ้า sub-agent ทำงานยาวต่อเนื่อง การตั้ง `subagentPromptCacheTtl` เป็น `1h` ช่วยให้ reuse cache ได้มากขึ้น แลกกับค่า cache write ที่สูงขึ้น ([Claude Code costs](https://code.claude.com/docs/en/costs)) และสุดท้าย ใช้ `/usage` ดูว่า token ไปอยู่ที่ sub-agent ตัวไหน ก่อนและหลังเปลี่ยนการตั้งค่า

สำหรับกฎใน CLAUDE.md ควรเขียนให้ Opus เป็นผู้เขียนโค้ดคนเดียว ให้ sub-agent ส่งกลับมาเป็นสรุปหรือ diff ที่ตรวจได้ ให้ Opus ตรวจคำอ้างของ sub-agent เช่น "เทสต์ผ่านครบ" ด้วยการรันเองก่อนเชื่อ และห้ามให้ sub-agent สองตัวแก้ไฟล์เดียวกัน

## บทสรุป

สิ่งที่เปลี่ยนไปในรุ่น 5.5 คือคำถามไม่ใช่ "ใช้ Opus หรือ Sonnet" อีกต่อไป แต่เป็น "ใช้ effort เท่าไร และให้ใครเป็นผู้เขียน" Opus 5.5 ถูกลงจนการใช้ Opus เดี่ยวเป็น baseline ที่แข็งแรงและตั้งค่าง่ายที่สุด ส่วน Sonnet 5.5 ใกล้เคียง Opus จนแทนได้ในงานที่ขอบเขตชัด แต่ความคุ้มค่านั้นหายไปทันทีที่ effort สูงขึ้นหรือเมื่อมีหลาย agent เขียนโค้ดพร้อมกัน ดังนั้นการตั้ง Sonnet 5.5 เป็น sub-agent จะให้ผลจริงก็ต่อเมื่อมันช่วยลดสิ่งที่ Opus ต้องอ่าน ไม่ใช่เพิ่มสิ่งที่ Opus ต้องตรวจ

เนื่องจาก Sonnet 5.5 เพิ่งออกมาหนึ่งวัน ควรถือการตั้งค่าข้างต้นเป็นสมมติฐานที่ต้องวัดเอง วิธีที่ตรงกับเกณฑ์ของ Anthropic คือเลือกงานจริง 5–10 ชิ้นจาก repo ของตัวเอง รันแบบ Opus 5.5 เดี่ยวที่ `medium` เทียบกับแบบ Opus ร่วมกับ Sonnet sub-agent แล้วดูสามค่า ได้แก่ token ใน `/usage` จำนวนรอบที่ต้องแก้งานซ้ำ และเวลาที่ใช้รีวิว ถ้าแบบลูกผสมชนะไม่ขาดทั้งสามค่า ให้กลับไปใช้ Opus เดี่ยวแล้วปรับเฉพาะ effort ภายในสองถึงสี่สัปดาห์ข้างหน้าน่าจะเริ่มมีรายงานการใช้งานจริงจากชุมชนและ system card ให้ตรวจตัวเลขที่ยังค้างอยู่ ควรกลับมาทบทวนกฎนี้เมื่อถึงตอนนั้น
