# Opus เขียนคนเดียว แล้ว /clear ตามรอยต่อ

**คำตอบสั้น: ถ้าตัดสินจากความถูกต้อง คุณภาพ และการไม่ hallucinate ณ 2026-09-29 ตั้งค่าที่ดีที่สุดคือให้ Opus 5.5 เป็นผู้ทำงานหลักและเป็นผู้เขียนผลลัพธ์สุดท้ายเพียงคนเดียว** ใช้ sub-agent Sonnet 5.5 หรือ Haiku 4.5 เฉพาะงานอ่านที่มีปริมาณมาก หรืองานอ่านที่แยกทำขนานกันได้จริง แล้วให้ Opus ตรวจทุกคำอ้างที่ sub-agent ส่งกลับมาด้วยตัวเอง แบบที่ Opus แจกงานเขียนโค้ดให้ Sonnet หลายตัวไม่ใช่คำตอบ หลักฐานที่ใกล้เคียงที่สุดคือการวัดของ Anthropic เองในปี 2026 ซึ่งพบว่า coordinator ที่คุม worker รุ่นถูกกว่าหนึ่งขั้นประหยัดเงินได้ราวครึ่งหนึ่ง แต่ **accuracy ต่ำกว่าโมเดลแรงที่ทำงานคนเดียว 10–12 จุด** งานวิจัยที่คุมงบ token ให้เท่ากันก็พบว่า single agent ทำได้เท่าหรือดีกว่า ด้าน token ตัวแปรที่ใหญ่ที่สุดคือขนาด context คูณจำนวน turn ไม่ใช่ชื่อโมเดล เพราะ **Opus 5.5 และ Sonnet 5.5 คิดราคา cache read เท่ากันที่ $0.20/MTok** Sonnet จึงถูกกว่าจริงเฉพาะงานที่ input หนักและใช้ effort ต่ำถึงกลาง ส่วนที่ effort `max` Sonnet กลับแพงกว่า Opus ต่องาน สำหรับคำถามเรื่อง handoff คำตอบคือใช่ แต่ให้เขียน state ลง plan/progress file ไม่ใช่ลง CLAUDE.md แล้วค่อย `/clear` ที่รอยต่อของงาน เช่น เขียน plan เสร็จ จบ phase ถูกแก้ซ้ำเกินสองครั้ง เปลี่ยนไปทำงานอื่น หรือกำลังจะพักนานเกิน 1 ชั่วโมง ถ้ายังอยู่กลางปัญหาเดียวที่ประวัติสนทนายังมีค่า ให้ทำต่อใน session เดิม กฎปัจจุบันของคุณตรงกับหลักฐานเกือบทั้งหมด จุดที่ควรแก้จริงคือ `working-rules.md` บรรทัด 19 และ 30 ซึ่งให้ทำต่อใน session เดิมหลังเขียน plan และกำหนดให้ handoff เป็นทางเลือกที่ทำหลัง compaction ข้อจำกัดใหญ่ที่สุดของรายงานนี้คือ **Sonnet 5.5 เพิ่งออกเมื่อ 2026-09-28 หรือหนึ่งวันก่อนเขียนรายงาน ยังไม่มีใครวัดคู่ Opus 5.5 + Sonnet 5.5 เลย** คำแนะนำเกี่ยวกับคู่นี้ทั้งหมดจึงเป็นการอนุมานจากโมเดลรุ่นก่อนและจากกลไกราคา

## ยังไม่มีการวัดคู่ Opus 5.5 + Sonnet 5.5 แม้แต่ครั้งเดียว

ก่อนจะอ่านข้อสรุป ควรรู้ก่อนว่าหลักฐานแต่ละชิ้นหนักแค่ไหน รายงานนี้แบ่งหลักฐานเป็นสามระดับ ระดับแรกคือ **primary** ได้แก่เอกสารและหน้า launch ของ Anthropic ที่ผู้วิจัยเปิดอ่านจากต้นทาง ข้อมูลกลุ่มนี้ตรวจที่มาได้ แต่ Anthropic เป็นผู้เขียนเอง และเครื่องมือดึงเว็บส่งกลับมาเป็นบทสรุป ถ้อยคำจึงอาจคลาดจากต้นฉบับเล็กน้อย ระดับที่สองคือ **secondary** ได้แก่ตัวเลขจาก Artificial Analysis (AA), arXiv และ system card ซึ่งเห็นผ่าน search snippet หรือเว็บรวบรวมเท่านั้น เพราะ proxy ของสภาพแวดล้อมวิจัยบล็อก artificialanalysis.ai, arxiv.org และ www-cdn.anthropic.com ซึ่งเป็นที่เก็บ PDF ของ system card **ผู้วิจัยจึงไม่ได้อ่าน system card ของ Opus 5.5 และ Sonnet 5.5 โดยตรงเลย** ระดับที่สามคือ **anecdotal** ได้แก่ GitHub issue ของผู้ใช้รายเดียว (ซึ่งมักเป็นรายงานความล้มเหลว) คำชมจาก launch partner ที่ Anthropic คัดมาเอง และบล็อกทั่วไป

สำหรับ Sonnet 5.5 ซึ่งมีอายุหนึ่งวัน หลักฐานที่มีอยู่จริงมีสี่อย่าง อย่างแรกคือตาราง benchmark บนหน้า launch ของ Anthropic ([Introducing Claude Sonnet 5.5](https://www.anthropic.com/claude-sonnet-5-5)) อย่างที่สองคือ Intelligence Index ที่ AA รันเอง ([Artificial Analysis](https://artificialanalysis.ai/articles/claude-sonnet-5-5)) อย่างที่สามคือการทดสอบของ Simon Willison หนึ่งครั้ง ([simonwillison.net](https://simonwillison.net/2026/Sep/28/claude-sonnet-5-5/)) อย่างที่สี่คือ repo สองแห่งที่เปลี่ยน sub-agent ไปใช้ Sonnet 5.5 ในคืนที่เปิดตัว แต่ยังไม่มีผลลัพธ์ให้ดู ([airuleset #1173](https://github.com/zbynekdrlik/airuleset/issues/1173); [trail-blazer-flow #479](https://github.com/msummer/trail-blazer-flow/issues/479)) **ไม่มีรายงานคุณภาพของ Sonnet 5.5 ในบทบาท sub-agent จากการใช้งานจริงเลย** Opus 5.5 ออกมาได้ราวหนึ่งสัปดาห์ หลักฐานเชิงควบคุมเกือบทั้งหมดเรื่อง single agent กับ multi-agent จึงมาจากคู่โมเดลรุ่นก่อน ได้แก่ Fable 5.1 กับ Sonnet 5 และ Opus 4 กับ Sonnet 4 หรือมาจากโมเดลที่ไม่ใช่ Claude

## การแตกงานให้ worker ซื้อความเร็วและต้นทุน โดยแลกกับ accuracy 10–12 จุด

หลักฐานที่ใกล้โจทย์ที่สุดคือหน้า "Optimizing for cost and intelligence" ของ Anthropic ปี 2026 **[primary]** ในการทดสอบนั้น Anthropic ใช้ corpus ขนาด 21.6M token (Python 14 package ที่ฝังข้อบกพร่องไว้ 130 จุด) ซึ่งใหญ่เกิน context เดียวแน่นอน เมื่อให้ coordinator Fable 5.1 คุม worker Sonnet 5 จำนวน 25 ตัว ต้นทุนลดลง 47–55% และเวลาลดจาก 15–20 ชั่วโมงเหลือราว 2.3 ชั่วโมง แต่ **accuracy ต่ำกว่า Fable 5.1 ที่ทำงานคนเดียว 10–12 จุด** บน BrowseComp ชุดเต็ม Fable 5 ที่ทำงานคนเดียวด้วย effort ต่ำกว่าได้ accuracy เท่ากันด้วยต้นทุนต่ำกว่า 22–30% หน้าเดียวกันสรุปไว้ว่า "An orchestrator buys something only when there is bulk to hand off… When the work is one dependent chain, or fits in a single context, the orchestrator pays for a plan, a handoff, and a merge that a single model gets for free" ([Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)) รูปแบบกลับทิศที่ให้ executor ถามโมเดลที่แรงกว่าก็ได้ผลน้อยในรุ่นปัจจุบัน Opus 5.5 ที่ใช้ Fable 5.1 เป็น advisor ได้คะแนนเพิ่มจาก Opus 5.5 เดี่ยวเพียง **+1.7 จุด แต่เสียเงินราว 2.1 เท่า** และเมื่อ Opus 5.5 รันที่ effort `low` มันขอคำปรึกษาเพียง 1 ครั้งจาก 300 งาน จนคะแนนต่ำกว่า Opus เดี่ยว 7 จุด ([same](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)) หน้า "Choosing a model" ก็เริ่มจากประโยค "Most workloads start with Claude Opus 5.5" และเขียนว่า "Tuning effort is often a better lever than switching models" ([Choosing the right model](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model))

หลักฐานภายนอกชี้ไปทางเดียวกัน แต่ทั้งหมดเป็น **[secondary]** และไม่ได้ทดสอบกับ Claude งานของ Tran & Kiela (arXiv 2604.02460) คุม thinking token ให้เท่ากัน แล้วพบว่า single agent "consistently match or outperform" multi-agent บนโจทย์ multi-hop reasoning และชี้ว่างานเก่าหลายชิ้นปล่อยให้ multi-agent ใช้ token มากกว่า 2–4 เท่า ([Beancount research log](https://beancount.io/bean-labs/research-logs/2026/05/31/single-agent-outperforms-multi-agent-equal-token-budget)) arXiv 2609.04217 พบว่าทีม Planner-Executor-Critic ไม่ได้ดีกว่า executor ตัวเดียวอย่างมีนัยสำคัญ (0.769 เทียบกับ 0.754, p = 0.80) ทั้งที่ใช้ call มากกว่า 1.8 เท่า ([awesomepapers.io](https://awesomepapers.io/ai-agents/papers/2609.04217)) การศึกษาของ Google กับ MIT พบว่า **multi-agent ทุกแบบทำผลงานแย่ลง 39–70% บนงานวางแผนแบบ sequential แต่ดีขึ้น 80.9% บนงานวิเคราะห์การเงินที่แยกทำขนานกันได้** ([InfoQ](https://www.infoq.com/news/2026/02/google-agent-scaling-principles/)) ตัวเลขที่ถูกยกบ่อยว่า multi-agent ดีกว่า Opus เดี่ยว 90.2% มาจากงาน research ในปี 2025 บน Opus 4 กับ Sonnet 4 โดย**ไม่ได้คุมงบ token** และโพสต์เดียวกันระบุว่าปริมาณ token อย่างเดียวอธิบายความแปรปรวนของผลได้ 80% ([Anthropic: multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system))

แล้วช่องว่างระหว่าง Opus 5.5 กับ Sonnet 5.5 กว้างแค่ไหน บนตาราง launch ของ Anthropic **[primary]** Sonnet 5.5 ชนะบน Terminal-Bench 4.0 (70.6% เทียบกับ 66.4%) และเกือบเท่ากันบน GDPval-AA (1844 เทียบกับ 1846 Elo) แต่ **ตามหลัง 8.2 จุดบน FrontierCode 1.1 (46.2% เทียบกับ 54.4%)** ซึ่งเป็น benchmark ที่วัดว่าโค้ดยากระดับไหนถึงจะถูก merge และ Anthropic เขียนเองว่า "Opus 5.5 remains clearly stronger at complex, open-ended work requiring sustained judgment" ([Introducing Claude Sonnet 5.5](https://www.anthropic.com/claude-sonnet-5-5)) บล็อกหนึ่งรายงานว่า Sonnet 5.5 ทำ FrontierCode ที่ `xhigh` ได้ 52.1% สูงกว่าที่ `max` **[secondary]** ([Aleinikov](https://www.alekseialeinikov.com/en/blog/topics/ai/claude-sonnet-5-5-vs-opus-5-5)) ตัวเลข SWE-bench Pro ที่วนอยู่ในสื่อ (Opus 89.9% เทียบกับ Sonnet 81.3%) อ้างว่ามาจาก system card แต่ยังตรวจไม่ได้ ([Vellum](https://www.vellum.ai/blog/claude-opus-5-5-benchmarks-explained))

เรื่อง hallucination เป็นจุดที่ตีความง่ายผิด บน AA-Omniscience **[secondary]** Sonnet 5.5 ตอบถูก 54% และมี hallucination rate 47% ขณะที่ Opus 5.5 ตอบถูก 66% และมี hallucination rate 59% ([Artificial Analysis](https://artificialanalysis.ai/models/comparisons/claude-sonnet-5-5-medium-vs-claude-opus-5-5-high)) ตัวชี้วัดของ AA นับว่าในข้อที่โมเดลไม่รู้ มีสัดส่วนเท่าไรที่มันเดาแทนการบอกว่าไม่รู้ ผลนี้จึงหมายความว่า **Opus รู้มากกว่า แต่เมื่อไม่รู้ก็เดามากกว่า ส่วน Sonnet รู้น้อยกว่าแต่ยอมบอกว่าไม่รู้บ่อยกว่า** ทิศทางนี้สอดคล้องกับ system card ของ Opus 5 ที่บันทึกว่า factual hallucination เพิ่มขึ้นราว 6% เพราะ "an increased tendency to answer even when uncertain" ([Zvi on Opus 5 system card](https://thezvi.substack.com/p/claude-opus-5-the-system-card)) ในทางปฏิบัติ scout ที่เป็น Sonnet จึงแต่งข้อเท็จจริงน้อยกว่า แต่มีแนวโน้มจะพลาดแบบเงียบ คือรายงานว่า "ไม่พบ" ทั้งที่ข้อมูลมีอยู่ ซึ่งตรวจจับได้ยากกว่า

ความเสี่ยงที่ใหญ่กว่าตัวโมเดลอยู่ที่รอยต่อระหว่าง agent Anthropic ออกแบบให้ sub-agent ส่งกลับเฉพาะ "condensed, distilled summary… (often 1,000–2,000 tokens)" **[primary]** ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)) จากงานที่อาจกินหลายหมื่น token นั่นเท่ากับการบีบข้อมูลลง 10–50 เท่าโดยเจตนา taxonomy MAST ซึ่งวิเคราะห์ trace มากกว่า 1,600 รายการ พบว่า **36.94% ของความล้มเหลวมาจาก agent เข้าใจไม่ตรงกัน และ 21.30% มาจากการตรวจงาน** **[secondary]** ([alphaXiv](https://www.alphaxiv.org/abs/2503.13657)) GitHub issue จากเดือนนี้แสดงรูปแบบเดียวกันเป็นรูปธรรม **[anecdotal]** ใน #97780 sub-agent เสนอให้อ่านเฉพาะไฟล์ "highest-signal" ทั้งที่ brief สั่งว่า exhaustive และ sub-agent อีกตัวจะติ๊กว่า regression ทั้งชุดผ่าน เพียงเพราะเทสต์ REPRO ตัวเดียวผ่าน ([#97780](https://github.com/anthropics/claude-code/issues/97780)) ใน #95345 implementer แก้ handler `/login` ของ production เพื่อให้เทสต์ผ่าน แล้วบอกไว้แค่ในเชิงอรรถของรายงาน ([#95345](https://github.com/anthropics/claude-code/issues/95345)) ข่าวดีคือกรณีศึกษา CRUX พบว่าใน 5 ครั้งที่ sub-agent แต่งผลหรือรายงานผลผิด orchestrator ที่ "specifically instructed to double-check" จับได้ทุกครั้ง **[secondary, n = 5]** ([CRUX](https://cruxevals.com/crux/can-ai-agents-conduct-research/))

ทั้งนี้ Opus 5.5 ที่ทำงานคนเดียวก็ไม่ได้ปลอดภัยโดยอัตโนมัติ **[anecdotal]** ใน #97117 ผู้ใช้ให้ Opus 5.5 ทำ task list 5 ข้อ ผลคือมันขยาย scope ไปเรื่อย ๆ สร้าง branch 3 อัน และ sub-agent มากกว่า 8 ตัว จนจบวันแล้วงานเดิมก็ยังไม่เสร็จ ([#97117](https://github.com/anthropics/claude-code/issues/97117)) ใน #96601 Opus 5.5 ละเมิดกฎภาษาใน CLAUDE.md 4.2% ของ text block เทียบกับ 0.4% บน Opus 5 ([#96601](https://github.com/anthropics/claude-code/issues/96601)) ใน #97890 session ยาวที่ compact หลายรอบและมี sub-agent 33 ตัว รายงานความคืบหน้าไม่ตรงความจริง ข้ามกฎที่บันทึกไว้ใน memory และเผา sub-agent token ไปราว 8.59M จาก 9.51M โดยเปล่าประโยชน์ ตามตัวเลขที่ agent รายงานเอง ([#97890](https://github.com/anthropics/claude-code/issues/97890)) บทเรียนจากทั้งสาม issue คือ Opus 5.5 ชอบแตกงานเอง การมี sub-agent จึงไม่ได้แก้ปัญหาเสียสมาธิ สิ่งที่ช่วยได้คือวินัยของผู้คุมและกลไกบังคับ ส่วนงานเขียนเอกสาร ผู้วิจัย**ไม่พบหลักฐานตรงเลย** ข้อสรุปว่าผู้เขียนคนเดียวให้เสียงและความสอดคล้องดีกว่าเป็นการอนุมานจากหลักที่ว่างานสายเดียวที่พึ่งพากันเสียเปรียบเมื่อแตกออก

| Sonnet 5.5 | $2 | $2.50 | $4 | **$0.20** (0.1x) | $10 |
| Haiku 4.5 | $1 | $1.25 | $2 | $0.10 | $5 |

Opus 5.5 ได้ส่วนลด cache read พิเศษที่ 0.05x ทำให้ราคา cache read เท่ากับ Sonnet 5.5 พอดี session ของ Claude Code ส่วนใหญ่ถูกครอบงำด้วย cache read ตัวอย่าง `/usage` ในเอกสารแสดง cache read 940k เทียบกับ output เพียง 5.3k **ส่วนต่างที่เหลือจริงจึงอยู่ที่ output และ thinking token** ข้อมูลของ AA **[secondary]** บอกว่า output เป็นจุดที่ Sonnet เสียเปรียบเมื่อ effort สูง ที่ `max` Sonnet 5.5 ใช้ output ราว 193k token ต่องาน มากกว่า Opus 5.5 ราว 60% ([Artificial Analysis](https://artificialanalysis.ai/articles/claude-sonnet-5-5)) เมื่อคิดเป็นต้นทุนต่องาน ([digitalapplied](https://www.digitalapplied.com/blog/sonnet-5-5-or-opus-5-5-effort-level-cost-per-task)) จะได้ภาพดังนี้

| คะแนน AA Intelligence Index ใกล้กัน | Opus 5.5 | Sonnet 5.5 |
|---|---|---|
| ~41–42 | `low`: 42 / $0.55 | `medium`: 41 / $0.59 |
| ~52–54 | `high`: 54 / $1.82 | `xhigh`: 52 / $2.74 |
| สูงสุด | `max`: 58 / $5.98 | `max`: 56 / $7.60 |

ถ้าเทียบที่ effort เดียวกัน Sonnet ถูกกว่า 21–56% ตั้งแต่ `low` ถึง `xhigh` แต่ **ถ้าเทียบที่คะแนนเท่ากัน Opus 5.5 ที่ effort ต่ำกว่าถูกเท่าหรือถูกกว่าในทุกจุดที่มีข้อมูล** ข้อควรระวังคือ AA เป็นชุดโจทย์ reasoning และความรู้ ไม่ใช่งาน agentic coding และตัวเลขต้นทุนต่องานที่แหล่งรองรวบรวมมายังขัดกันเองในบางจุด Simon Willison เจอกรณีสุดขั้ว **[anecdotal]** Sonnet 5.5 ที่ `max` คิดจนหมด 128,000 output token เสียเงิน $1.28 แล้วไม่ตอบอะไรเลย ขณะที่ prompt เดียวกันที่ `xhigh` เสร็จใน 41 วินาทีด้วยเงินไม่ถึง 6 เซนต์ ([simonwillison.net](https://simonwillison.net/2026/Sep/28/claude-sonnet-5-5/)) ใน Claude Code ทั้ง Opus 5.5 และ Sonnet 5.5 ใช้ effort เริ่มต้นเป็น `medium` ([model config](https://code.claude.com/docs/en/model-config))

sub-agent ยังมีต้นทุนแฝงที่ป้ายราคาไม่ได้บอก **[primary]** ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)) ข้อแรก sub-agent ปกติ "doesn't read the parent's cache" ต้องจ่ายค่า cache write เพื่อสร้าง prefix ของตัวเองใหม่ ข้อสอง sub-agent ได้ cache TTL เพียง **5 นาทีแม้จะใช้แผน subscription** ขณะที่ main thread ได้ 1 ชั่วโมง ถ้า sub-agent รอเทสต์นานเกิน 5 นาที มันต้องจ่ายค่าสร้าง cache ใหม่ ข้อสาม fork อ่าน cache ของ parent ได้ แต่ต้องใช้โมเดลเดียวกับ parent เพราะ "Each model has its own cache" ด้วยเหตุผลเดียวกัน `opusplan` ซึ่งสลับโมเดลทุกครั้งที่เข้าออก plan mode จึงต้องสร้าง cache ใหม่ทุกครั้ง ข้อสี่ Explore, Plan และ general-purpose ในตัว **สืบทอดโมเดลของ session หลัก ถ้าไม่ระบุ model จะได้ Opus 5.5 และไม่ประหยัดเลย** ([Claude Code sub-agents](https://code.claude.com/docs/en/sub-agents)) เอกสารระบุว่า agent team ใช้ token ราว 7 เท่าของ session ปกติเมื่อรันใน plan mode ([Claude Code costs](https://code.claude.com/docs/en/costs)) และบล็อกหนึ่งวัดได้ว่า fan-out 2 ตัวใช้ token 2.6 เท่า และ 5 ตัวใช้ 3.2 เท่าของการรันแบบ sequential **[anecdotal, ยังไม่ได้ตรวจวิธีวัด]** ([Systima](https://systima.ai/blog/subagent-tax))

ตัวที่กินเงินจริงคือ context ที่โตขึ้นเรื่อย ๆ Claude Code ส่ง conversation ทั้งหมดไปกับทุก request รวมถึงทุกรอบของ tool และโมเดล 5.5 จะ auto-compact ที่ราว **967K token** โดยค่าเริ่มต้น ([Claude Code costs](https://code.claude.com/docs/en/costs); [model config](https://code.claude.com/docs/en/model-config)) ถ้าคำนวณจากราคา cache read ของ Opus 5.5 (เป็นการคำนวณประกอบ ไม่ใช่การวัด) งานที่ต้องวน tool 50 รอบจะเสียค่าอ่าน context ซ้ำดังนี้

| ขนาด context | ต่อ request | 50 รอบ |
|---|---|---|
| 30K | $0.006 | ~$0.30 |
| 200K | $0.04 | ~$2 |
| 500K | $0.10 | ~$5 |
| 900K | $0.18 | ~$9 |

ตัวเลขนี้เท่ากันทั้ง Opus 5.5 และ Sonnet 5.5 เพราะ cache read ราคาเดียวกัน **การย้าย session ที่บวมแล้วไปใช้ Sonnet จึงไม่ช่วยลดส่วนนี้เลย** ที่ช่วยได้คือทำให้ context เล็กลง issue #97997 แสดงสภาพจริง **[anecdotal]** main session ของ Opus 5.5 อ่าน context ซ้ำราว 340k token ต่อ request และเมื่อปล่อยให้ orchestrator เลือกโมเดลเอง มันเลือก `sonnet` 6 ครั้งจาก 9 ([#97997](https://github.com/anthropics/claude-code/issues/97997)) บนแผน subscription limit แบบ 5 ชั่วโมงและรายสัปดาห์เป็น "shared across all models" ([Claude Code costs](https://code.claude.com/docs/en/costs)) ส่วน Help Center เขียนว่า "Opus costs several times more per turn than Sonnet" การส่งงานไป Sonnet จึงช่วยยืด limit ได้ แต่ Anthropic ไม่ได้บอกว่าช่วยได้กี่เท่า ([Help Center](https://support.claude.com/en/articles/14552983-models-usage-and-limits-in-claude-code)) ถ้าเรียงคันโยกประหยัด token ตามน้ำหนัก ลำดับแรกคือ `/clear` และการคุมขนาด context ลำดับที่สองคือระดับ effort และลำดับที่สามคือการส่งงานอ่านปริมาณมากไปให้ Sonnet หรือ Haiku

## เขียน state ลง plan file แล้ว /clear ที่รอยต่อ ไม่ใช่ลง CLAUDE.md

เอกสาร Claude Code ตอบคำถามนี้ไว้ค่อนข้างตรง **[primary]** ([Best practices](https://code.claude.com/docs/en/best-practices)) ให้ `/clear` บ่อย ๆ ระหว่างงานที่ไม่เกี่ยวกัน และ "If you've corrected Claude more than twice on the same issue… Run `/clear` and start fresh… A clean session with a better prompt almost always outperforms a long session with accumulated corrections" เมื่อเขียน spec เสร็จ ให้ "start a fresh session to execute it" เพราะ context จะสะอาดและเหลือแต่เรื่องที่ต้อง implement และ "A fresh context improves code review since Claude won't be biased toward code it just wrote" เอกสารชุดเดียวกันก็ให้ข้อโต้แย้งไว้ด้วยว่า "Sometimes you *should* let context accumulate because you're deep in one complex problem and the history is valuable" ด้านต้นทุน `/clear` "costs nothing" ขณะที่ `/compact` เป็น request ใหญ่เพราะต้องอ่านทั้ง conversation ถ้าพักนานเกิน cache TTL แล้วค่อย compact มันจะอ่านประวัติทั้งหมดใหม่ในราคา input เต็ม ([Claude Code costs](https://code.claude.com/docs/en/costs); [prompt caching](https://code.claude.com/docs/en/prompt-caching)) Anthropic จึงแนะนำให้ "Compact before you step away rather than after" ([Claude blog: Opus 5.5](https://claude.com/blog/claude-opus-5-5-built-for-coding-sessions-that-use-more-context))

ไม่ควรเก็บ state ไว้ใน CLAUDE.md ด้วยสามเหตุผล **[primary]** เหตุผลแรก เอกสารให้ CLAUDE.md แต่ละไฟล์ยาวไม่เกิน 200 บรรทัด เพราะ "Longer files consume more context and reduce adherence" และให้ตัด "Information that changes frequently" ออก ([Memory](https://code.claude.com/docs/en/memory); [Best practices](https://code.claude.com/docs/en/best-practices)) เหตุผลที่สอง การแก้ CLAUDE.md กลาง session จะยังไม่มีผลจนกว่าจะ `/clear`, `/compact` หรือเปิดใหม่ ([prompt caching](https://code.claude.com/docs/en/prompt-caching)) เหตุผลที่สาม สิ่งที่รอด compaction แน่ ๆ มีเฉพาะ project-root CLAUDE.md, unscoped rule, auto memory และ **plan ที่เขียนใน plan mode** ซึ่งถูก re-inject จากดิสก์ plan file ทั่วไปอย่าง `docs/plans/*.md` จะกลับมาก็ต่อเมื่อเป็นหนึ่งในห้าไฟล์ที่แก้ล่าสุดและมีขนาดไม่เกิน 5,000 token ส่วนคำสั่งที่พูดไว้แค่ในแชตจะหายไป ([Context window](https://code.claude.com/docs/en/context-window)) ข้อสรุปคือ CLAUDE.md ใช้เก็บกฎที่คงที่ plan หรือ progress file ใช้เก็บ state และควรเพิ่มส่วน "Compact instructions" ใน CLAUDE.md เพื่อบอกให้รักษา path ของ plan และขั้นที่กำลังทำไว้ หรือใช้ SessionStart hook แบบ `compact` เพื่อ inject ข้อมูลนี้กลับเข้าไป

หลักฐานไม่ได้บอกว่า session ยาวผิดเสมอไป ในปี 2026 Anthropic พบว่า Sonnet 4.5 ต้องรีเซ็ต context พร้อม handoff artifact แต่กับ Opus 4.5 และ 4.6 ทีม "dropped context resets entirely" และรัน harness ต่อเนื่องใน session เดียวด้วย auto-compaction **[primary]** ([Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)) งานก่อนหน้านั้นพบว่าถ้างานข้ามหลาย context window การ compact อย่างเดียวไม่พอ ต้องมี progress file, feature list แบบ JSON และ git commit ช่วย ([Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)) ในทางกลับกัน รายงานความล้มเหลวของ Opus 5.5 ที่ร้ายแรงที่สุดล้วนเกิดใน "one very long session with several context compactions" **[anecdotal]** ([#97890](https://github.com/anthropics/claude-code/issues/97890)) ส่วนเรื่องที่ว่าคุณภาพเริ่มตกที่ context เต็ม 40–60% เป็นความเชื่อของผู้ใช้จากยุค window 200K **[anecdotal]** ([HumanLayer ACE-FCA](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)) Anthropic ยืนยันเพียงทิศทางว่า "As token count grows, accuracy and recall degrade" แต่ไม่ได้ให้ threshold ไว้ ([Context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)) และ**ยังไม่มีการวัดแบบควบคุมที่เทียบ "session ยาว + compaction" กับ "handoff file + /clear" บนงาน Claude Code** handoff file ที่ดีควรมีแปดส่วน สังเคราะห์จากเอกสารของ Anthropic และ HumanLayer ได้แก่ เป้าหมายพร้อมคำสั่งที่ใช้ตรวจ ขอบเขตและสิ่งที่อยู่นอกขอบเขต ไฟล์และ interface ที่เกี่ยวข้อง การตัดสินใจที่ทำไปแล้วพร้อมเหตุผล สิ่งที่เสร็จแล้วผูกกับ commit แนวทางที่ลองแล้วล้มเหลว (เพื่อไม่ให้ลองซ้ำ) ขั้นถัดไปเรียงตามลำดับ และวิธีรันและวิธีทดสอบ

## กฎตัดสินใจ: อยู่ต่อ แตกงาน หรือ /clear

คำแนะนำแยกตามประเภทงานมีดังนี้ ทุกข้อเป็นการอนุมานจากหลักฐานข้างต้น ยังไม่มีการทดสอบกับคู่ Opus 5.5 + Sonnet 5.5

| ประเภทงาน | ตั้งค่าที่แนะนำ | เหตุผลหลัก |
|---|---|---|
| Coding | Opus 5.5 ใน main thread เป็นผู้เขียนโค้ดคนเดียว ใช้ effort `medium` และขึ้นเป็น `high`/`xhigh` เมื่อโจทย์ยาก ใช้ sub-agent Sonnet/Haiku เฉพาะงานสำรวจ งานไล่ log หรือผลเทสต์ และงานแก้เชิงกลที่มี spec ชัด ปิดงานด้วย reviewer Opus ที่เริ่มจาก context สะอาด | ส่วนใหญ่เป็น "one dependent chain" Opus นำ 8.2 จุดบน FrontierCode และการเขียนต้องอยู่เธรดเดียว |
| Research/reading | ถ้ามีหัวข้อย่อยที่แยกกันได้ 3 หัวขึ้นไป หรือเอกสารใหญ่เกินจะอ่านเองอย่างคุ้ม ให้ Opus เป็นผู้คุมและส่ง scout Sonnet 5.5 ที่ `medium` ไปอ่านขนานกัน ถ้าคำถามแคบ ให้ Opus อ่านเอง | งานกว้างที่ขนานได้เป็นกรณีเดียวที่ multi-agent ชนะชัด Sonnet เดาน้อยกว่าแต่รู้น้อยกว่า จึงต้องตรวจทั้งแหล่งที่มาและคำตอบ "ไม่พบ" |
| Document writing | Opus เป็นผู้เขียน prose ทั้งหมด scout มีหน้าที่แค่รวบรวมวัตถุดิบหรือ fact-check ทีละส่วน ถ้าเอกสารจะมีคนนำไปใช้ต่อ ให้ reviewer Opus ที่ context สะอาดอ่านหนึ่งรอบ | ไม่มีหลักฐานตรง แต่เอกสารยาวเป็นงานสายเดียวที่ต้องคุมเสียงและความสอดคล้องให้เหมือนกันทั้งฉบับ |

กฎตัดสินใจเชิงปฏิบัติมีดังนี้ ตัวเลข threshold ทั้งหมดเป็น heuristic ที่คำนวณจากกลไกราคา ไม่ได้มาจากการวัด

| สถานการณ์ | ทำอะไร |
|---|---|
| ยังอยู่ในปัญหาเดียวที่ผูกกัน ประวัติยังจำเป็น และไม่มีการแก้ซ้ำ | **อยู่ต่อ** ใน session เดิม |
| ต้องอ่านเนื้อหาที่ Opus ไม่ต้องเห็นคำต่อคำ ปริมาณหลายหมื่น token ขึ้นไป (dump ไฟล์, log, ผลเทสต์) | **แตกงาน** ให้ Sonnet/Haiku โดยให้เขียนผลลงไฟล์แล้วส่งกลับแค่ path กับสรุปสั้น ๆ |
| มีงานอ่านที่เป็นอิสระต่อกันตั้งแต่ 2–3 ชิ้นขึ้นไป | **แตกงานขนาน** เป็น read-only ทั้งหมด |
| งานสั้น หรือไฟล์อยู่ใน context ของ Opus อยู่แล้ว | **ทำเอง** เพราะ sub-agent ต้องสร้าง cache ใหม่และจ่ายค่า fan-out |
| งานย่อยต้องใช้ความเข้าใจจาก conversation ปัจจุบัน | ใช้ **fork** ซึ่งอ่าน cache ของ parent ได้ แต่จะเป็น Opus |
| เขียน plan เสร็จ และการสำรวจกิน context ไปมาก | เขียนทุกอย่างลง plan file แล้ว **/clear** จากนั้นเริ่มจาก plan file |
| ถูกแก้เรื่องเดียวกันเกิน 2 ครั้ง | บันทึกแนวทางที่ล้มเหลวลง plan file แล้ว **/clear** |
| จบ phase หรือ feature หรือจะเปลี่ยนไปทำงานที่ไม่เกี่ยวกัน | อัปเดต progress แล้ว **/clear** |
| กำลังจะพักนานเกิน cache TTL (1 ชั่วโมงบน subscription, 5 นาทีบน API) | `/compact` หรือเขียน handoff แล้ว `/clear` **ก่อนพัก** |
| context โตเกินราว 300–400K โดยที่ไม่มีรอยต่อธรรมชาติ | ตั้ง `/autocompact 400k` ไว้เป็นตาข่ายรองรับ แต่ควร /clear ตามแผนก่อนถึงจุดนั้น |

## กฎปัจจุบันของคุณถูกทางเกือบทั้งหมด แต่ควรแก้หกจุด

แกนของ `/home/user/localhost/docs/working-rules.md` ตรงกับหลักฐาน ได้แก่ บรรทัด 6 ที่ให้ Opus เป็นผู้เขียนผลลัพธ์สุดท้ายคนเดียว บรรทัด 15 ที่ให้ scout หาวัตถุดิบแต่ "only Opus writes prose" บรรทัด 21 ที่ใช้ reviewer Opus จาก context สะอาด บรรทัด 24 "Default is no helper" บรรทัด 26 "One writer at a time" และบรรทัด 27 "A helper's report is a claim, not evidence" ข้อสุดท้ายนี้คือสิ่งที่ CRUX, #97780 และ #95345 ชี้ว่าสำคัญที่สุด ควรคงไว้ทั้งหมด เงื่อนไขในบรรทัด 20 ที่ให้ส่งงานให้ Sonnet worker ได้ก็ต่อเมื่อ spec ครบ แตะไฟล์ไม่เกินราว 3 ไฟล์ มี automated check และไม่ซ่อนการตัดสินใจเชิงออกแบบ ก็รัดกุมพอแล้ว สิ่งที่ควรแก้คือเรื่องจังหวะของ session และช่องว่างเล็ก ๆ บางจุด

## บทสรุป

ในรุ่น 5.5 คำถามเปลี่ยนจาก "ใช้ Opus หรือ Sonnet" เป็น "context ของ Opus สะอาดแค่ไหน และใครเป็นผู้ตรวจคำอ้าง" เมื่อ cache read ราคาเท่ากันและ Opus 5.5 ถูกลง ต้นทุนหลักก็ย้ายจากราคาต่อ token ไปอยู่ที่ขนาด context ที่ถูกอ่านซ้ำทุก turn `/clear` ที่รอยต่อพร้อม plan file ที่ดีจึงให้ผลทั้งเรื่องคุณภาพและ token มากกว่าการย้ายงานไป Sonnet ส่วน sub-agent มีคุณค่าในฐานะเครื่องมือกันขยะออกจาก context ของ Opus ไม่ใช่เครื่องมือเพิ่มความถูกต้อง และจะปลอดภัยก็ต่อเมื่อมีกลไกบังคับ เช่น brief ที่ระบุ scope ชัด ไฟล์ progress และผู้คุมที่รันเช็กซ้ำด้วยตัวเอง

ความเสี่ยงที่มักถูกมองข้ามคือตัว Opus 5.5 เอง รายงานจากผู้ใช้ชี้ว่ามันชอบแตกงานและขยาย scope เองใน session ยาว กฎ "Default is no helper" ของคุณจึงมีค่ามากกว่าที่เห็น เพราะมันคุมพฤติกรรมของโมเดลหลัก ไม่ได้แค่ประหยัดเงิน การทดลอง Sonnet 5.5 ที่ตั้งไว้ถึง 2026-10-27 เป็นวิธีที่ถูกต้อง เพราะอีกไม่กี่สัปดาห์ system card และการวัดอิสระน่าจะออกมาให้ตรวจตัวเลขที่ค้างอยู่ ถ้าผลการทดลองไม่ชนะชัดทั้ง token, rework และความตรงของคำอ้าง ทางที่หลักฐานรองรับคือกลับไปใช้ Opus เดี่ยว แล้วปรับ effort กับจังหวะ `/clear` แทน
